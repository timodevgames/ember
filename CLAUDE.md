# Ember — habits, food & a fox spirit

Timo's gamified life tracker: habits (piano, Valorant, Geometry Dash, …) and a free
Yazio-style food/protein tracker, glued together by a pet that lives or leaves
depending on how consistent he is. **UI language: English.**

Full product plan: `docs/PLAN.md` (approved 2026-10-13). Phases 1–5 there.

## Commands

- `npm run dev` — dev server on port 5180 (also `.claude/launch.json` → "ember")
- `npm test` — vitest (engine, schedule, nutrition, sync)
- `npm run build` — typecheck + production build (PWA, service worker)
- `npm run build:server` / `npm run deploy:server` — bundle `server/` with esbuild and ship it to the Pixel (`ssh termux`), printing `/health` (version = git sha + build time) as proof it's live
- `npm run build:food` — regenerate `public/data/foods-bls.json` from the BLS zip in `scripts/data/bls/`
- `npm run icons` — re-render PNG icons from `public/icons/icon.svg` (macOS QuickLook)
- Dev-only page `/dev/pets` shows every pet stage × mood.

## Architecture

- **Vite + React 19 + TS + Tailwind v4 + Dexie + vite-plugin-pwa.** Dark UI, ember-orange accent, `ui-rounded` font.
- **Local-first.** Everything lives in IndexedDB (`src/db/db.ts`). Every synced record has `id`, `updatedAt` (REAL wall-clock ms), `deleted` (0/1 tombstone) and `deviceId`. **All writes go through `src/db/repo.ts` (`save`/`remove`)** so metadata is set and the future sync client is notified. Never `db.x.put` directly for synced tables.
- **The game is never stored.** `src/core/game/engine.ts` `replay()` folds over every day from the pet's `startDay` and recomputes HP, bond XP, coins, streaks, freezes, run-away/rescue and finds from the logs. All balance numbers live in `src/core/game/rules.ts`; changing them re-scores history. Randomness is seeded by the day string (`dayRandom`) so replays are stable.
- **Past days are settled, today is a projection.** Today credits XP/coins immediately, but HP/streak change only when the day ends. The pet's first day (`startDay`) can heal but never hurt (`firstDayGrace`).
- **Logical days** (`src/core/date.ts`): a day starts at `prefs.dayStartHour` (default 04:00). Day strings are parsed at local noon so DST never breaks arithmetic. Tests pin `TZ=Europe/Berlin`.
- **Schedules** (`src/core/habits/schedule.ts`): `daily | weekdays | perWeek`. A per-week habit is `open` until skipping would make the weekly goal impossible, then `due`; done days count as `due` until the goal is met, after that as `bonus`. Manual and auto logs for the same habit/day merge by **max**.
- **Manual log ids are deterministic** (`m:<habitId>:<day>`), auto-check ids too (`auto:<source>:<habitId>:<day>`) — so two devices / repeated server runs merge into one record instead of duplicating.
- **Editing window:** today and yesterday only (Today page toggle). Vacation mode starts today at the earliest — it can't erase past days.
- **Sandbox** (`src/core/sandbox.ts`): separate DB `ember-sandbox` + a day offset ("time machine") for testing the game. `nowMs()` is the only clock game code may use. `updatedAt` always uses real `Date.now()`.
- `src/state/game.tsx` — `GameProvider` live-queries Dexie and runs `replay()` once per change; components read it via `useGame()`.
- `src/features/<area>/` — today, habits, pet (PetView SVG, shop), settings, onboarding, events (one-time pop-ups for evolve/find/run-away/rescue, de-duplicated via `meta.seenEvents`).
- **Nutrition** (`src/core/nutrition/`): `targets.ts` (Mifflin–St Jeor × activity, goal delta, protein g/kg, 7-day weight trend advice), `foods.ts` (`FoodItem` = BLS row / OFF product / custom food / recipe, `scale()`), `search.ts` (dependency-free; folds umlauts, ignores spaces so "haferflocken" finds "Hafer Flocken", ranks own foods/favourites/usage first), `portions.ts` (hand-made portion table matched on German names — BLS is per 100 g only), `off.ts` (Open Food Facts v3 product + search-a-licious, direct from the browser; OFF allows CORS), `barcode.ts` (native `BarcodeDetector` if it supports EAN, else zxing-wasm with the **bundled** wasm via `?url` — never the CDN default).
- **Food data file:** `public/data/foods-bls.json` is generated by `node scripts/build-food-db.mjs <BLS_4_0_Daten_2025_DE.xlsx>` from the BLS 4.0 zip (blsdb.de/download, CC BY 4.0 — credit the Max Rubner-Institut). Raw zip lives in `scripts/data/bls/` (gitignored). Compact arrays `[code, de, en, kcal, protein, carbs, fat, fiber, sugar, salt]`.
- **Food logs snapshot nutrients** at logging time. Scanned products are cached into `foods` on first use (`off:<barcode>`); favouriting a BLS food stores a marker row with the BLS id. Nutrition goals (`settings.nutritionGoals`) carry `since` — earlier days are never re-scored when goals are set or changed. Protein ≥ 90 % and 2+ meals (and optionally calories ≥ 90 %) become day items in the game.
- **Sync** (`src/state/sync.ts` ↔ `server/`): local-first; the app never waits for the network. Push = this device's records (`deviceId === me`) with `updatedAt > sync.lastPushAt` (the very first push sends everything, incl. backup imports); pull = everything after the server `seq` cursor. Both sides keep the newer `updatedAt` (ties keep the existing row). Remote rows are written with plain Dexie calls — never `repo.save` — so they don't echo. Triggers: launch, local change (1.5 s debounce), tab visible, online, every 60 s. Sync is off in the sandbox. Pairing code = `ember:` + base64url `{url, token}`; connecting to a server that already has data asks "use synced data (wipe this device)" vs "merge".
- **Wire protocol** (`src/core/sync/protocol.ts`): only CORS-simple POSTs (`text/plain` JSON, token in the body) — no preflight, and ngrok's free-tier browser warning never triggers for these. `GET /health` is public.
- **habits-api** (`server/`): `node:http` + `node:sqlite`, zero runtime deps, one `records(tbl,id,updatedAt,seq,data)` table + `off_cache` (Open Food Facts proxy with a real User-Agent, 30-day cache). Runs on the Pixel under pm2 as `habits-api` on 127.0.0.1:3040, behind edge-proxy `/habits` → `https://paraesthetic-hilary-guidingly.ngrok-free.dev/habits`. `.env` holds `SYNC_TOKEN`; `~/apps/habits-api/pairing.sh` prints the pairing code. Server ops details live in `Pixel Server/CLAUDE.md`.
- **Auto-checks** (`server/integrations/`): `runner.ts` runs 15 s after start, every 30 min, and on `POST /integrations/run` (the app's "Check now", throttled to 10 s). It reads habits + the synced settings `integrations` (Riot ID, GD username, Music Coach port, time zone) and `prefs` (day start) from its own store — falling back to `.env` (`RIOT_ID`, `RIOT_REGION`, `GD_USERNAME`, `MUSIC_COACH_PORT`, `HENRIK_API_KEY`) — and writes `habitLogs` with fixed ids `auto:<source>:<habitId>:<day>` only when the value changed, for the last 7 days and never before a habit's `createdDay`. Logical days are computed in the user's IANA zone (`days.ts`), never the phone's. Sources: Music Coach's own sync file (`~/apps/Music-Couch/server/data/sync-<port>.json`, minutes from `startedAt/endedAt`), HenrikDev v4 matches + v3 MMR (header `Authorization: <key>`), GDBrowser profile (done when any counter rose vs. the last snapshot of an earlier day; the first snapshot is a baseline). Per-day stats go to `integrationStats` `stat:<source>:<day>`, the last result per source to `status:<source>`. These server rows don't count as "existing data" when pairing a new device.
- **Counters must be atomic:** use `addHabitValue` (read + write in one Dexie transaction) for +1/+5 taps — "props value + 1" loses fast taps.
- **PetView** is pure SVG with SMIL animation (SMIL keeps SVG coordinate semantics in Safari; CSS transforms on SVG groups don't). Tail count/size/extras come from `RULES.stages`.

## Conventions

- Custom CSS classes that utilities must be able to override go in `@layer components` (unlayered CSS beats Tailwind utilities in v4).
- Pure logic in `src/core/**` with tests next to it (`*.test.ts`, node env).
- iPhone is the main device: test at 375×812, respect safe areas (`pt-safe`/`pb-safe`), inputs ≥16px.

## Deploy

GitHub Pages via `.github/workflows/pages.yml` (sets `BASE_PATH=/<repo>/`, copies `index.html` → `404.html`). An installed web app keeps its data per origin, so the URL must never change.
